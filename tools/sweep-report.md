## 1. 세로 여백 — 늘리지 말고 채운다

### 옛 판에서 확인된 것 (mysql-btree/README.md)

레인을 `flex:1 1 auto` 로 늘려 남는 높이를 흡수하게 하니 카드가 592px 이 되었지만
내용은 그대로 가운데 떠서 **여백이 카드 밖에서 안으로 옮겨간 것뿐**이었다 (카드마다 400px 공백).
답은 남는 높이를 *내용* 에 주는 것이다 — 무대는 필요한 만큼만(`flex:0 1 auto`),
그 아래 슬롯이 나머지를 받는다(`flex:1 1 0`, 기준 0 이라 발췌가 길어도 무대를 밀지 않는다).

### 이 판에서 한 것 (`src/style.css`)

    .app{height:100vh; display:flex; flex-direction:column}   /* min-height → height */
    .top,.tabs,.head,.bar,.play,.cap,.foot{flex:0 0 auto}     /* 줄어들 것은 무대뿐 */
    .wrap{flex:1 1 auto; min-height:0; min-width:0}
    .mid{flex:0 1 auto; min-height:0; display:flex; flex-direction:column}
    .mid:has(> .srcin,> .slot,> .fill){flex:1 1 auto}   /* 슬롯이 있을 때만 자란다 */
    .mid > .stage,.mid > .stage-wrap{flex:0 1 auto}     /* 무대는 내용만큼만 */
    .mid > .slot,.mid > .fill{flex:1 1 0; min-height:0} /* 슬롯 계약 (기준 0) */

`height` 로 바꾼 이유 : `min-height:100vh` 이면 초광폭의 `height:calc(100vh / zoom)` 이
성립하지 않는다. 아주 낮은 창(높이 < 640px)은 가두면 캡션이 조용히 잘리므로
`@media (max-height:639px){ .app{height:auto;min-height:100vh} }` 로 풀어 준다.

`flex:0 0 auto` 를 준 이유 : flex 항목의 기본 `flex-shrink:1` 때문에 높이가 모자랄 때
캡션 글자가 먼저 줄었다. 줄어들 것은 무대 하나여야 한다.

`:has()` 를 쓴 이유 : 슬롯이 없을 때 `.mid` 가 자라면 여백이 `.mid` 안으로 옮겨갈 뿐이다
(옛 판에서 레인을 늘려 실패한 것과 같은 종류). 슬롯이 있을 때만 자란다.

### 실측 (1512×982, 인라인 소스가 슬롯을 차지한 상태)

    book-ch3/02/1   카드 111·111·111  무대 123  소스 490.9  → .mid 안 남는 높이 0
    innodb/01/1     카드 118·118·118·168  무대 333  소스 없음 → .mid 안 남는 높이 292.9

슬롯(`.srcin`)을 DOM 에서 제거해도 아무 것도 무너지지 않는다 —
무대 높이 123 그대로, 캡션 위치 851.4 그대로, 남는 502.9px 이 `.mid` 밑에 남는다.
카드 높이가 내용과 같다는 것(111px 카드 / 111px 내용)이 요점이다 :
옛 판의 592px 카드 문제가 재발하지 않았다.

**남은 여백은 슬롯의 표시 조건이 정한다.** 발췌가 없는 스텝에서는 `.mid` 안에
최대 503px 이 빈다. 그 판단은 `src/Source.jsx` (다른 에이전트) 소관이다 — 8장 참조.

## 2. 반응형

### 초광폭 — 더 많이가 아니라 더 크게

    @media (min-width:2000px){ .app{zoom:1.25; height:calc(100vh / 1.25)} }
    @media (min-width:2560px){ .app{zoom:1.5;  height:calc(100vh / 1.5)} }
    @media (min-width:3400px){ .app{zoom:2;    height:calc(100vh / 2)} }
    @media (min-width:4600px){ .app{zoom:2.5;  height:calc(100vh / 2.5)} }
    @media (min-width:4600px){ #app.app{zoom:2.5; height:calc(100vh / 2.5)} }  /* 8장 참조 */

`height` 를 배율로 나눠야 한다 — `zoom` 은 `100vh` 를 해석한 뒤 곱하므로 그대로 두면 넘친다.
스윕의 `zoom-height` 검사가 이것을 지킨다.

**배율은 코드 줄높이 16px 을 정수로 유지하는 값만 쓴다** :
16×1.25=20 · ×1.5=24 · ×2=32 · ×2.5=40. 1.3·2.6 은 20.8·41.6 이 되고 브라우저가
스크롤을 장치 픽셀로 양자화할 때 줄 경계가 깨진다(옛 판 실측 235/600 회).
스윕의 `zoom-lineheight` 검사가 이것을 지킨다 — `--break=zoom` 으로 1.3 을 넣으면 발동한다.

### 768 ~ 1080px — 뷰포트에 맞추지 않는다

    .app{height:auto; min-height:100vh; padding:14px 16px}   /* 페이지가 스크롤된다 */
    .stage{flex:none; overflow:visible}                      /* 그래서 잘리지 않는다 */
    .top .tabs{flex:1 0 100%}                                /* 탭은 자기 줄로 */

실측(innodb/01/1) : 1024·1080 에서 레일이 무대 아래로 내려가 4열로 펼쳐지고
(`.mid` y=197 / `.rail` y=865 · 4열), 페이지가 스크롤되고, 가로 스크롤은 0 이다.
1100 에서는 레일이 250px 오른쪽 열로 돌아오고 페이지 높이가 뷰포트에 묶인다(825=825).
경계 1080/1100 양쪽이 의도대로 갈린다.

탭 띠 실측 : 자연폭 885px. 768 에서 2줄(높이 52) · 1024 이상에서 1줄(26) ·
**모든 폭에서 가로 스크롤 0**. 이 판의 App.jsx 는 `.tabs` 를 `.top` 밖의 자기 줄에
두었으므로 옛 판의 "brand 와 한 줄을 못 나눈다" 문제는 발생하지 않는다.
`.top` 안으로 들어오는 경우를 대비해 `.top .tabs{flex:1 0 100%}` 를 남겨 뒀다.

### 767px 아래 — 만들지 않는다

    .narrow-note{display:none}        /* ← 반드시 @media 보다 앞 */
    @media (max-width:767px){
      .narrow-note{display:block}
      .app .stage-wrap,.app .stage,.app .stage-foot,.app .tabs,.app .bar,.app .play{display:none}
    }

**기본 규칙을 미디어 쿼리 앞에 둔다.** 뒤에 두면 같은 특이도로 `display:block` 을 덮어서
안내가 영원히 안 뜬다. `--break=narrow` 가 이 순서를 뒤집어 재현한다(11/11 검출).

**`.app` 를 앞에 붙여 특이도를 (0,2,0) 으로 올렸다.** 미디어 쿼리 안이라도
*다른 파일의 뒤 규칙* 은 같은 특이도면 이긴다 — `rail.css` 가 `style.css` 뒤에 실리므로
`.play{display:flex}` 가 `@media` 안의 `.play{display:none}` 을 이겼고,
스윕이 767 아래에서 재생 막대가 보이는 것을 11/11 로 잡았다. 같은 사고의 파일 간 판본이다.

`.narrow-note` **요소는 아직 App.jsx 에 없다** — CSS 만 준비했다. 8장 참조.
확인은 `--inject-note` 로 요소를 끼워 넣어서 했다 : 390·767 에서 문제 0,
순서를 뒤집으면(`--break=narrow`) `narrow-note-hidden` 11건.

### 셸에서 고친 실제 문제 둘

- **`.act{min-width:0}` 이 카드의 바닥을 없앴다.** 옛 판 실측으로 1100px 에서 45px 까지
  짜부라졌다. `min-width:96px` ("비었다" 26px 이 들어가는 최소폭) + `.row{flex-wrap:wrap}` —
  넘치는 대신 줄을 넘긴다. 좌표를 가진 종류(축·트리·그래프)는 236px 이 필요하다 → 8장.
- **`.it` 이 접히지 않아 `hold` 태그가 페이지를 넘었다.** 768px 에서 155px 카드에서
  태그가 카드를 28.5px, 페이지를 3px 넘어 **가로 스크롤 3px** 이 생겼다.
  `.it` 의 자손은 `min-width:auto` 라 min-content 아래로 줄지 않는다.
  id·tag 는 식별 정보라 자르지 않고 `flex-wrap:wrap;row-gap:3px` 로 접었다.
  고친 뒤 768·834·1024·1080 에서 `page-hscroll` 0.

## 3. 스윕 — `tools/sweep.js`

덱 × 장면 × 스텝 × 폭을 전부 돈다. 폭은 미디어 쿼리 경계 양쪽을 낀다 :
`768 · 834 · 1024 · 1080 · 1100 · 1366 · 1512 · 1559 · 1561 · 1728 · 2000 · 2560 · 3440 · 5120`.
높이는 그 폭의 실제 장치를 따른다(100vh 를 쓰므로 높이가 결과를 바꾼다).
**비교 모드(V)** 도 함께 돈다 — 옛 판에서 접힌 배우 24개가 전부 빈 띠였던 문제가
이 모드에만 있었고 그때까지 한 번도 스윕된 적이 없었다.

### 측정 코드를 열세 번 틀렸다 — 그 목록이 곧 설계다

1. **선택자가 틀려 0 스텝을 돌고 "문제 0" 을 보고했다.**
   → 방문 수를 항상 함께 출력한다. 거기에 렌더된 스텝 번호(`.play .track[aria-valuenow]`)를
   요청값과 대조해 **확인** 수를 따로 센다. `확인 < 방문` 이면 통과가 아니다.
   *이번에도 걸렸다* : 다른 에이전트가 `.bar` 를 `Playback` 으로 바꿔서
   `.bar button` 을 세던 코드가 0 을 돌려주고 스윕이 통째로 멈췄다.
2. **퇴장 애니메이션이 `opacity:0` 으로 끝나는데 그것을 넘침으로 셌다** (옛 판 오탐 102건).
   → `offsetParent !== null` 과 조상 사슬의 `visibility:hidden`/`display:none`/`opacity<.05`.
3. **`scrollWidth`/`scrollHeight` 로 넘침을 재려 했다** — 정수로 반올림되고 어느 쪽인지 모른다.
   → 보이는 자손의 `getBoundingClientRect()` 를 컨테이너 상자와 비교한다.
4. **오른쪽만 봤다** — 실제 문제 6건이 왼쪽으로 나가 있었다. → 좌·우·상·하 모두 본다.
5. **일부러 스크롤되는 곳을 넘침으로 셌다** (오탐 650 + 400건).
   → 자손과 컨테이너 사이에 `overflow-x/y:auto|scroll` 이 있으면 건너뛰고,
   컨테이너 자신이 스크롤되는 *축* 은 그 축을 건너뛴다.
   **선택자 목록으로 관리하지 않는다** — 계산된 스타일로 판정한다.
   목록으로 두면 다른 에이전트가 새 스크롤 상자를 만들 때마다 오탐이 돌아온다.
6. **여러 줄로 흐른 글자를 잘렸다고 셌다.**
   → flex 아이템은 몇 줄을 흘러도 `getClientRects()` 가 한 개만 준다.
   내용에 `Range` 를 걸어 *줄 조각* rect 를 얻고 **칸** 의 상자와 비교한다.
7. **라벨 겹침은 컨테이너를 넘지 않으므로 넘침 검사로 영원히 안 잡힌다.**
   → 형제 라벨 rect 를 쌍으로 비교해 두 축이 모두 겹치면 실패.
8. **zoom 상태에서 좌표계를 섞었다.** `getBoundingClientRect()` 는 zoom 이 곱해진 값,
   `getComputedStyle` 의 padding/border 는 안 곱해진 CSS px 이다.
   → `currentCSSZoom` 으로 환산한다. 안 섞으면 zoom 2.5 에서 6px 씩 틀린다.
9. **애니메이션 도중에 쟀다.** rect 를 정수로 반올림한 서명은 스프링의 마지막
   `scale 0.9995` 를 놓쳐서 **1.5px 넘침 8건을 오보**했다.
   → 0.1px 서명 + `transform` 문자열 + `getAnimations()` 가 멎을 때까지 기다린다.
10. **일부러 스크롤되는 상자의 가로 넘침은 스크롤바·`hidden` 에 숨는다** (옛 판 650건).
    → `overflow-x` 가 `hidden|clip` 인데 `scrollWidth` 가 넘치면 따로 보고하고,
    `auto|scroll` 이면 의도된 가로 스크롤이므로 넘긴다.
    `text-overflow:ellipsis` 도 의도된 잘림이므로 넘긴다 —
    `.steps li span` 때문에 오탐 49건이 나왔다.
11. **기준 상자를 하나로 봤다.** 흐름 안의 자손은 *내용 상자* 에 배치되지만
    절대 위치 자손의 담는 상자는 *패딩 상자* 이고 `overflow` 도 패딩 경계에서 자른다.
    내용 상자로만 재면 `.ax{padding:35px 12px 26px}` 에서 한 스텝에 11건이 쏟아졌다.
12. **축·그래프·트리를 다른 상자처럼 쟀다.** 이 종류는 라벨을 자르면 어느 구간인지
    알 수 없으므로 삐져나올 자리를 스스로 `margin` 으로 남긴다(`Axis.jsx` 의 주석).
    실측 : 1512px 에서 `.ax-sp` 가 패딩 상자를 좌 11px·우 13px 넘지만 `.ax{margin:0 22px}`
    안이고 카드는 37px 여유가 있다. **진짜 경계는 카드(`.act`)** 이고 그것은 따로 잰다.
    상자 목록에서 빼고, 라벨 겹침 검사에는 남긴다.
13. **해시 이동은 같은 문서 안의 이동이라 `page.goto` 로도 문서가 새로 실리지 않는다.**
    덱을 바꾸면 App 은 `deckName` 을 즉시 바꾸지만 덱 모듈은 dynamic import 로 나중에 온다.
    그 사이 탭의 href 는 `#새덱/앞덱의 장면번호/1` 이 되어 **어떤 검사로도 구별되지 않는다**.
    실측 : 계획이 실행마다 달라졌고(장면 22/23 · 스텝 104/105), 768px 에서
    스텝 불일치 29건이 나왔다 — *앞 덱의 장면을 새 덱의 것으로 재고 있었다.*
    → 덱을 바꿀 때는 쿼리를 붙여(`/?deck=x#x`) 문서를 정말 새로 싣는다.
    그리고 **계획 지문**(장면별 스텝 수)을 함께 출력해 실행 간 흔들림을 볼 수 있게 했다.
    교훈 1 과 같은 종류이고, 이번 회차에서 가장 오래 숨어 있던 것이다.

### 자동 재생을 끈다

`reducedMotion:'reduce'` 로 컨텍스트를 연다. `App.jsx` 는 `REDUCED` 일 때 자동 재생을
하지 않는다. 끄지 않으면 재는 동안 스텝이 저절로 넘어가 측정이 통째로 어긋난다.

### 검사 일곱

| 검사 | 무엇을 보는가 |
|---|---|
| `overflow` | 상자 안의 보이는 자손이 좌·우·상·하로 나갔는가 (흐름=내용 상자 / 절대=패딩 상자) |
| `text-clip` | 고정폭 칸 안에서 `Range` 줄 조각이 칸을 넘었는가 |
| `label-overlap` | 형제 라벨이 두 축 모두 겹쳤는가 |
| `page-hscroll` | 페이지에 가로 스크롤이 생겼는가 (`html{overflow:hidden}` 이어도 잡힌다) |
| `hidden-hclip` | `overflow-x:hidden|clip` 인데 내용이 넘쳐 **안 보이게** 잘렸는가 |
| `zoom` / `zoom-lineheight` / `zoom-height` | 배율이 맞는가 · 16px×배율이 정수인가 · `calc(100vh/zoom)` 이 걸렸는가 |
| `narrow-*` | 767 아래에서 안내가 뜨고 무대·탭·재생이 감춰졌는가 |
| `step-mismatch` | 요청한 스텝이 정말 렌더됐는가 (측정 자체의 신뢰도) |

## 4. 검사가 정말 발동하는지 — 일부러 망가뜨렸다

발동하지 않는 검사는 무가치하다. `--break=NAME` 으로 각 사고를 재현했다.
전부 확인 뒤 원상복구했다(`--break` 는 런타임에만 스타일을 끼워 넣고 파일을 고치지 않는다).

| `--break` | 무엇을 망가뜨렸나 (옛 판의 실제 사고) | 잡힌 것 |
|---|---|---|
| `overflow` | `.row{flex-wrap:nowrap}` + `.act{min-width:520px}` — 1100px 에서 카드가 45px 로 짜부라진 자리 | `overflow` 1,545건 (`.stage-wrap`·`.scol`·`.stage`·`.row` 에서 최대 553.1px) + `hidden-hclip` 11 |
| `text-clip` | `.a-hd{width:16px;overflow:hidden}` — 16px 띠의 내용 상자가 2px 로 줄어 이름이 통째로 잘린 자리 | `text-clip` 43건 (`.a-hd` 안 `.a-nm` 49.2px · `.a-ct` 85.1px) + `hidden-hclip` 43 + `overflow` 26 |
| `label-overlap` | 형제 라벨을 `position:absolute; left:0; top:0` 으로 겹침 — 축 라벨이 `c0<c2020..39` 로 읽힌 자리 | `label-overlap` 124건 (`.foot` 에서 11px 겹침 등) |
| `zoom` | `#app{zoom:1.3; height:100vh}` — 1.3 이 16px 줄높이를 20.8 로 깨뜨린 자리 + height 를 배율로 안 나눈 자리 | `zoom` 11 (원한 1.5 / 얻은 1.3) · `zoom-lineheight` 11 (20.8) · `zoom-height` 11 (324px 초과) |
| `narrow` | `.narrow-note{display:none}` 을 `@media` **뒤** 로 옮김 — 안내가 영원히 안 뜬 자리 | `narrow-note-hidden` 11/11 |

같은 설정에서 망가뜨리지 않으면 `overflow`·`text-clip`·`label-overlap` 은 0,
`zoom` 세 검사는 0, `narrow` 는 390×844 에서 0 이다
(`--widths=1366 --decks=book-ch2 --every=20 --split=0` · zoom 은 `--widths=2560` ·
narrow 는 `--widths=390`).

`step-mismatch` 와 `page-hscroll` 은 일부러 망가뜨리지 않아도 발동했다 :
전자는 교훈 13(덱 경합)에서 29건, 후자는 768px 의 `.it` 태그 넘침에서 1건.
`hidden-hclip` 은 `.steps li span` 오탐 49건과 무대 스크롤러 2건으로 발동을 확인했다.
정상 상태에서 이 검사들은 0 이다.

## 부록 — 교훈 14·15 (전수 스윕에서 새로 드러난 것)

### 교훈 14 : 정착 서명에 `.by-c` 가 없어 overflow 36건이 거짓 양성이었다

14폭 전수 스윕(방문 4,410)에서 zoom 폭 4개만 문제를 냈다 :

| 폭 | zoom | 보고된 문제 |
|---|---|---|
| 2000×1125 | 1.25 | overflow 3 |
| 2560×1080 | 1.5 | overflow 9 |
| 3440×1440 | 2 | overflow 12 |
| 5120×2160 | 2.5 | overflow 12 |

상세가 정체를 알려 줬다 — `by` 0.8~1.3px 에 `clipped:false`, 요소는 전부
`div.by-c.…**new**` 였다. `new` 는 그 스텝에 *막 붙은* 칸이다.

프레임마다 추적해 확정했다 :

    3440  애니메이션 중 최대 넘침 453.43px · 정착 후 0px      (옛 빌드)
    3440  애니메이션 중 최대 넘침 453.43px · 정착 후 0px      (새 빌드)

`SETTLE` 은 `.act,.lane,.row,.cap,.head,.a-bd,.srcin,.scol` 의 서명만 봤다.
**바이트 칸은 이 목록에 없다.** 조상이 멎은 뒤에도 칸이 계속 움직이므로
"정착" 판정이 먼저 떨어지고, 그 뒤 한 프레임을 재면 애니메이션 꼬리
(0.8~1.3px)가 넘침으로 잡힌다. 배율이 클수록 이동 거리가 길어 꼬리도 길다 —
그래서 zoom 폭에만 나타났다.

`.by,.by-c,.mx,.tr` 를 서명에 넣어 고쳤고, 원인이 도구임을 **같은 빌드에서** 증명했다 :

| 실험 | 결과 |
|---|---|
| 고친 도구 × **옛** 빌드 (4폭) | 문제 **0** · 옛 지표(무대초과 108/115 · 소스보임 9/85)는 그대로 |
| 고친 도구 × `--break=overflow` | overflow **1,349** + hidden-hclip 14 |

첫 줄이 36건이 인공물이었음을, 둘째 줄이 검사가 여전히 발동함을 보인다.
둘 다 필요하다 — 거짓 양성을 없애면서 검사를 멀게 해서는 안 된다.

### 교훈 15 : zoom 은 실효 높이를 줄이지만 미디어쿼리는 확대 전 뷰포트를 본다

`@media (max-height:880px)` 크롬 압축층은 초광폭에서 **발동하지 않았다** :

| 폭×높이 | zoom | 실효 높이 | `(max-height:880px)` |
|---|---|---|---|
| 2560×1080 | 1.5 | **720** | false |
| 3440×1440 | 2 | **720** | false |
| 5120×2160 | 2.5 | **864** | false |
| 2000×1125 | 1.25 | 900 | false (900>880 이라 맞다) |

내용은 720px 안에 들어가는데 쿼리는 1080·1440 을 본다. 그래서 문턱을
`880 × zoom` 으로 올려 폭 조건과 함께 나열했다 (1.25→1100 · 1.5→1320 ·
2→1760 · 2.5→2200). 효과는 문제 수가 아니라 **지표**로 나타난다 :

| 폭 | 무대초과 | 소스보임 | 캡션아래 |
|---|---|---|---|
| 2560×1080 | 108 → **33** | 9/85 → **17/85** | 38 → **29** |
| 3440×1440 | 115 → **40** | 9/85 → **16/85** | 50 → **38** |
| 5120×2160 | 0 → 0 | 51/85 → **58/85** | 63 → **48** |

`zoom` 을 쓰는 곳에서는 `min-width` 로 배율을 고르고 `max-height` 문턱도
같은 배율로 곱해야 한다. 한쪽만 하면 이 구멍이 생긴다.

### 교훈 16 : 접힌 소스 패널의 빈 자리는 스페이서로 고칠 수 없다 (두 번 실패)

1366×768 에서 book-ch3+locks 130스텝 중 74스텝이 소스 패널을 접고(SRC_MIN 184 미달)
그 자리에 **합 7,642px · 최대 190px** 의 빈 띠를 남긴다. 무대는 위로 붙는다.

패널의 `flex` 를 건드리면 `offsetHeight` 로 "다시 띄울 수 있나" 를 판단할 수 없으므로
(`Source.jsx` 주석) 패널은 두고 무대 위에 같은 몫의 스페이서를 넣어 반씩 나누려 했다.
두 번 시도해 두 번 실패했다 — 둘 다 측정이 잡았다.

| 시도 | 방식 | 결과 |
|---|---|---|
| ① | React 상태 `srcVisible` 로 `.mid.nosrc` 부여 | 소스보임 **전멸** — 초기값 `false` 라 첫 페인트에 이미 스페이서가 들어가고, 온전했다면 350px 을 받아 보였을 패널이 175px 만 받아 184 미달로 판정되어 영구히 숨었다 |
| ② | `.mid:has(> .srcin.small)::before` (초기값 false 이므로 ①의 마운트 문제는 없다) | 소스보임 56 → **13** (43%→10%) · 빈 띠 7,642 → **9,453 증가**. 스텝 전환 중 무대가 순간 커지면 `small` 이 일시적으로 켜지고, 그 순간 스페이서가 붙어 368px 없이는 돌아오지 못한다 |

②의 이력(184 → 368) 추론은 `small` 이 *일시적으로* 켜질 수 있다는 점을 빼먹었다.
숨은 패널이 남는 높이의 **온전한 몫**을 계속 받아야 "다시 띄울 수 있나" 가 유효하다 —
B 의 `visibility:hidden` 설계는 취향이 아니라 구조적 요구다.

**결론 : 손대지 않는다.** 고치려면 패널의 flex 가 아니라 *발췌 데이터* 를 바꿔야 한다
(짧은 화면용으로 줄 수가 적은 발췌를 따로 두는 식). 그건 CSS 문제가 아니다.

### 교훈 17 : 좁은 폭 문제는 CSS 가 아니라 "레인당 카드 수" 에서 고친다

전수 스윕(14폭 · 4,410방문 · 확인 4,186 · 불일치 0)의 문제 39건은 **두 곳에만** 모였다 :

| 폭 | 문제 |
|---|---|
| 768 · 834 | text-clip 3 · 2 (비교 모드 `.kv`) |
| **1100×825** | **34** (overflow 24 · text-clip 10) |
| 그 밖 11폭 | 0 |

CSS 로 세 번 고치려 했고 세 번 되돌렸다 (`.kv` 감김은 1366 에서 문제 0→20 회귀).
원인은 층을 잘못 짚은 것이다 — 좁은 컨테이너에 긴 내용을 넣는 문제는
**무대에 몇 장을 올리는가** 로 풀어야 한다.

먼저 카드가 *원하는* 폭을 쟀다(`max-width` 를 풀고 `width:max-content`, zoom 1 구간에서) :

| 덱 | 필요폭 최대 | 90% | 50% |
|---|---|---|---|
| innodb | **422** (`innodb/07/1` STATEMENT) | 371 | 231 |
| book-ch2 | 334 | 236 | 197 |
| book-ch3 | 384 | 281 | 208 |
| locks | (행렬은 `max-content` 에서 폭발 — 제외) | 335 | 246 |

이 값으로 계산이 맞아떨어진다 : 1100 의 행 폭은 691 이라 2장이면 338px 씩 —
422 에 못 미쳐 긴 SQL 이 카드 가장자리까지 밀렸다. 1366 은 행 폭 957 이라
2장에 472px 씩으로 충족되고, 실제로 그 폭은 문제 0 이었다.

그래서 `Stage` 가 행 폭을 재서 `floor((행폭 + 14) / (422 + 14))` 로 레인당 상한을 정하고,
넘치면 이 스텝이 건드린 카드를 남긴다. `useLayoutEffect` 로 페인트 전에 정해 첫 화면부터
맞게 그리고, `ResizeObserver` 로 폭 변화를 따른다.

**zoom 을 반드시 나눠야 한다** — `getBoundingClientRect` 는 배율만큼 커진 값을 준다.
나누지 않으면 초광폭에서 행이 실제보다 넓다고 판단한다(교훈 15 와 같은 함정).
실측으로 확인 : 2560(zoom 1.5) · 3440(zoom 2) 모두 행 폭 **1246 CSS px** 로 같게 읽힌다.

| 폭 | 행폭 | 카드 | 카드폭 | 내용 초과 |
|---|---|---|---|---|
| 1024×768 | 918 | 4 | 452 | 없음 |
| **1100×825** | 691 | **4→2** | **338→520** | **없음** |
| 1366×768 | 957 | 4 | 472 | 없음 |
| 1512 · 1728 | 1103 · 1246 | 4 | 520 | 없음 |
| 2560 · 3440 | 1246 | 4 | 520 | 없음 |

부작용은 정직히 적어 둔다 : **1024 에서 4장인데 1100 에서 2장이다.**
1080 위에서는 레일이 250px 를 가져가 행이 좁아지기 때문이다. 쌓임 문턱을 1250 으로
올리면 1100 도 4장을 유지하지만 그 층은 `height:auto` 라 페이지가 스크롤된다 —
"한 화면에 한 순간" 을 깨므로 올리지 않았다.

### 교훈 18 : 검사 대상을 없애서 통과하는 수정 — 스윕 0 은 무해함을 뜻하지 않는다

교훈 17 의 "레인당 카드 수" 수정은 스윕 14폭 4,410방문에서 **문제 0** 을 냈고
1100 의 34건과 768·834 의 5건을 전부 없앴다. 그런데 카드 손실을 세어 보니 :

| 행폭 (폭) | 카드 잃는 스텝 | 잃은 카드 |
|---|---|---|
| 691 (1100) | **338/338 (100%)** | **612** |
| 957 (1366) | 162/338 (48%) | 197 |
| 1246 (1728·2560) | 162/338 (48%) | 197 |

덱별로는 book-ch2 가 스텝의 91%, book-ch3 가 76% 에서 카드를 잃었다.

**스윕이 통과한 이유는 검사 대상을 없앴기 때문이다.** 스윕은 넘침을 재고
정보 손실은 재지 않는다. 글자가 카드 안쪽 4.5px 을 침범하는 것(잘림·숨김 없음)을
없애려고 카드 612장을 지운 셈이다.

원인은 `CARD_NEED = 422`(innodb 최댓값)를 **모든 덱에** 적용한 것이다.
덱별 값(book-ch2 334 · book-ch3 384 · locks 335)을 써도 1100 에서 84% 가 남는다 —
즉 문턱을 다듬어 해결되는 문제가 아니다. 카드를 *지우는* 방식 자체가 틀렸다.

되돌렸다. 되돌리는 스크립트가 `Card` 컴포넌트와 `count` 함수까지 잘라내
화면이 백지가 됐고(`Card is not defined`), 이 프로젝트는 git 저장소가 아니며
소스맵도 없어 **빌드 번들의 축약 코드에서 두 함수를 복원했다**
(`count` 는 앞서 읽어 둔 원본과 축약본이 정확히 일치해 대조 확인, `Card` 는
번들의 JSX 구조를 그대로 되살림). 복원 후 페이지 오류 0 · 카드 전부 표시.

**남겨 둘 규칙 두 개 :**

1. 검사가 0 이 됐을 때 "무엇이 줄어서 0 이 됐는가" 를 따로 세라.
   넘침을 재는 검사는 내용을 지우면 반드시 통과한다.
2. 되돌릴 수 없는 편집을 하기 전에 되돌릴 수단을 먼저 만들어라.
   이 프로젝트는 git 저장소가 아니어서 번들 역공학으로 복구해야 했다.

남은 39건(1100 의 34 · 768 의 3 · 834 의 2)은 전부 "정보는 보이지만 여유가 없다" 는
성질이다. 다시 시도한다면 카드를 없애지 않는 방향 — 행 줄바꿈으로 아랫줄에 배치 —
이어야 하고, 그건 세로 스크롤과의 교환이므로 카드 수와 스크롤량을 **둘 다** 재서
판단해야 한다.
